# 개선 제안을 받는 길

hanlint 를 쓰다가 만난 오탐 (정당한 문장을 잡음), 미탐 (잡아야 할 자리를 놓침), 불편 (출력, 명령,
문서) 은 버리지 않고 적는다. 접수는 두 길이고 형식이 같다. **문장 원문이 없는 제안은 접수가 아니다.**

## 바깥 기여자: GitHub Issues

`.github/ISSUE_TEMPLATE/` 의 두 양식을 쓴다.

- **오탐 신고**: 잡힌 문장 원문, 규칙 이름, `hanlint --version`, 왜 정당한 문장인지
- **규칙 제안**: 실제 글에서 가져온 나쁜 문장, 왜 나쁜지의 근거 (국립국어원 조항, 실측), 잡아야 할
  예시와 잡지 말아야 할 예시 한 개 이상씩

## 이 기계의 에이전트: mainPlan 대기열

전역 규칙이 한국어 산문에 hanlint 를 강제하므로, 다른 저장소에서 글을 쓰다 발견한 것도 여기로 온다.
소비 저장소에 영구 우회 (disable, 인라인 제어) 로 숨기지 않는다. 이 저장소의
`mainPlan/<번호>-<camelCase이름>/README.md` 에 새 항목을 만들고 다음을 적는다.

- 무엇을 하다가 (저장소, 글, 명령), 정확한 버전
- 잡힌 (또는 놓친) 문장 원문과 규칙 이름
- 기대와 실제, 왜 오탐 (미탐) 이라고 판단했는지
- 제안 (패턴을 좁히는 방향, spare 후보 문장)

같은 내용이 이미 있으면 새 항목 대신 그 항목에 사례를 더한다. 번호는 기존 대기열의 다음 수다.

## 처리

접수가 곧 수용이 아니다. 판정과 수리는 `operation.addingARule` 의 절차 (오탐은 fixture 의 spare 에
먼저 박고 규칙을 고친다. 실측 사례 없는 규칙은 만들지 않는다) 를 그대로 따른다. 받아들이지 않은
제안은 이유를 적어 닫는다. 릴리즈 이력이 이 길이 실제로 돈 증거다. 0.0.7 로 오는 동안 오탐 셋
(compare URL 속 점 셋, 버전과 날짜로 끝나는 절 제목, 로 로 끝나는 낱말 뒤 `로의`) 이 전부 이 꼴로
잡혀 좁혀졌다.
