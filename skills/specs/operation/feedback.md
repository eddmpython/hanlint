# 개선 제안을 받는 길

[GitHub Issues](https://github.com/eddmpython/hanlint/issues/new/choose)에서 내용에 맞는 양식을 고른다.
이미 접수한 내용인지 먼저 검색하고, 같은 문제라면 재현 사례를 더한다.

## 무엇을 남기나

| 내용 | 양식과 필요한 정보 |
|---|---|
| 정당한 문장을 잡았다 | 오탐 신고. 원문, 규칙, 검사 버전, 글 종류와 정당한 이유 |
| 실제 결함을 놓쳤다 | 규칙 제안. 실제 문장, 근거, 잡아야 할 예시와 잡지 말아야 할 예시 |
| 편집기나 명령이 예상과 다르다 | 사용 문제·수정 사례. 환경, 재현 순서, 관찰한 결과와 기대 |
| 안내가 없거나 잘못됐다 | 사용 문제·수정 사례. 문서 링크와 막힌 자리 |
| 직접 고친 글을 공유한다 | 사용 문제·수정 사례. 수정 전후, 글 종류, 수정 이유와 사람이 고친 범위 |

검사 버전은 CLI의 `hanlint --version`이나 편집기 하단에서 확인한다. 브라우저 문제에는 웹 주소와
브라우저 이름을 함께 적는다. 특정 문장의 판정을 바꾸자는 제안에는 재현할 수 있는 원문이 필요하다.
화면과 문서 문제에 원고 전문을 요구하지는 않는다.

비공개 내용은 지우거나 같은 지적을 재현하는 예문으로 바꾼다. 토큰과 인증 정보를 첨부하지 않는다.
아이디어 단계의 논의는 [Discussions](https://github.com/eddmpython/hanlint/discussions)에서 시작할 수 있다.

## 편집기에서 수정 사례 보내기

편집기의 ‘내 기록’에서 공유할 수정본을 골라 사례 파일을 내려받는다. 파일에는 수정 전후 전문과
글 종류, 검사 버전, 수정 이유와 방식이 들어간다. 공유할 내용을 확인한 뒤 Issues에 직접 첨부한다.
파일을 내보내는 동작은 외부 제출이 아니다.

‘이 지적은 맞지 않아요’로 남긴 판단은 개인 기록에 들어간다. 이 판단과 고침 기억의 승인도 운영자에게
자동으로 전달되지 않는다. 보관과 내보내기의 사용 절차는
[사용과 저장 안내](https://eddmpython.github.io/hanlint/guide.html#contribute)가 소유한다.

## 검토와 반영

개인 기록, 재사용 승인과 공통 규칙 반영을 구분한다. 수정 전후가 있다고 품질 정답으로 인정하지 않고,
어떤 조건에서 그 고침이 맞는지와 다른 문장에서 오탐을 만드는지 확인한다.

규칙의 판정과 수리는 [규칙을 더하고 고치는 절차](addingARule.md)를 따른다. 오탐은 잡지 말아야 할
fixture로 먼저 남기고 규칙을 좁힌다. 새 규칙에는 실측 사례와 양쪽 예시가 필요하다.
받아들이지 않은 제안에는 이유를 남기며, 반영한 변경은 테스트와 Git 이력으로 추적한다.
