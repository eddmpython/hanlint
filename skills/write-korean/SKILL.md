# hanlint 로 한국어 글 쓰기

hanlint 는 글을 만들지 않는다. 세어서 확정되는 결함을 잡고, 규칙마다 고치는 법과 본보기를 준다. 이 스킬은
그것을 쓰기 전에 읽고 쓰는 동안 검사하는 여섯 단계다. 좋은 글의 기준 (독자, 목소리, 구조) 은 사용자
저장소의 글쓰기 규칙이 소유하고 그것이 이 스킬보다 우선한다.

설치는 없다. 파이썬이 있으면 `uvx hanlint`, Node 만 있으면 `npx hanlint` 다. 아래의 `hanlint` 를 그것으로 읽는다.

## 여섯 단계

쓰기 전에 독자, 글을 읽은 뒤 할 판단, 반드시 전달할 사실을 짧게 정한다. 새로운 사실을 본보기에서 만들지 않는다.
수치와 구조를 지켜야 하는 글은 `start.readerContract`의 선택 계약을 쓰고 절마다 같은 계약으로 확인한다.
사실 잠금은 표현 보존 장치이며 자연스러움 향상 전략의 채택 근거와 구분한다.

1. **종류를 정한다.** 블로그 `blog`, 보고서 `report`, 참고 문서와 명세 `docs`, 단계별 안내 `guide`, 수필
   `essay`, 소설 `fiction`, 백과 `encyclopedia`. 실제 결과물과 같은 것을 골라 아래 명령에 `--preset <종류>` 로
   붙인다. 저장소에 `hanlint.toml` 이 있으면 그 설정을 따르고 옵션을 붙이지 않는다.
2. **primer 를 읽는다.** `hanlint primer --preset <종류>` 한 장이다. 켜진 규칙마다 고치는 법과, 잡히는 글 (전) 과
   같은 뜻으로 통과하는 글 (후) 한 쌍이 한 줄씩이다. 문체가 정해져 있으면 `--register 한다|합니다|해요` 로 그
   문체의 본보기를 받는다. 쓰기 전에 한 번 읽는다. 본보기의 사실과 숫자는 결과에 옮기지 않는다. 사용자가 숫자
   확인표를 요청했거나 분량을 별도로 점검해야 하면 `hanlint spec --preset <종류> --chars <글자 수>`도 읽는다.
   18편 실측에서 기본 채택 조건을 못 넘었으므로 모든 작문 프롬프트에 자동으로 붙이지 않고 primer와의 결합 효과도
   가정하지 않는다.
3. **쓰려는 용어의 쓰임을 본다.** 종류의 낱말을 모르고 쓰면 쉬운 말로 풀어 버린다 (`수취` 를 `받을` 로, `투자금액` 을
   `투자한 금액` 으로). 절에 들어갈 핵심 용어 두셋을 `hanlint usage "낱말" --kind <종류> --format json` 으로 묻는다.
   `words` 가 그 낱말 바로 뒤에 오는 용언 (`리스부채` 뒤에 인식 416편, 측정 132편) 과 앞뒤 명사를 문서 수로 주고,
   `hits` 가 실제 문장을 준다. 문서 수가 많은 결합을 고르고 문장의 사실과 숫자는 옮기지 않는다. 색인이 없으면 2 로
   끝나며 만드는 법을 알린다. 만들지는 사용자가 정한다 (`hanlint usage kinds` 가 있는 종류를 센다). 실측: 용례가
   있으면 강한 모델이 보고서의 낱말을 지키는 짝이 6, 잃는 짝이 1 이었다 (tests/_attempts/usageLift).
4. **절 하나를 쓰고 검사한다.** 절 (제목 하나와 그 아래 문단들) 을 다 쓰면 파일 전체를
   `hanlint 글.md --preset <종류>` 로 검사한다. 절마다 하는 이유는 둘이다. 결함이 다음 절로 번지기 전에 잡고,
   약속 회수와 수 대조처럼 두 자리를 견주는 규칙이 글이 자라는 대로 판정된다. 글이 파일이 아니라 손에 있으면
   `hanlint - --path 글.md` 로 stdin 에 넣는다. Claude Code에 PostToolUse `hanlint hook`이 연결돼 있으면 저장 직후
   같은 Finding이 다음 모델 요청에 자동으로 들어온다. 훅이 있어도 절을 넘기기 전 error 0은 명시 검사로 확인한다.
5. **error 를 0 으로 만든다.** 먼저 `hanlint fix 글.md` 로 기계가 확실히 고치는 자리를 적용한다. 남은 error 는
   지적의 이유와 후보 (`--format json` 의 `candidates`, `fix`, `patch`) 로 그 자리만 고친다. 후보는 정답이 아니라
   뜻에 맞는 것을 고르는 재료다. 뜻을 확정할 수 없으면 원문을 두고 사람에게 묻는다. 지적을 없애려고 문장이나
   사실을 지우지 않는다. 고친 뒤 4 를 다시 돌린다. 고치는 행위가 새 결함을 만든다.
   반복 상한과 개선하지 못한 후보의 처리는 `use-hanlint`의 5단계를 따른다.
6. **사람에게 넘긴다.** error 0 은 세어서 잡히는 결함이 없다는 뜻뿐이다. 사실, 뜻, 유용성, 자연스러움은 사람이나
   별도 평가자가 본다. 넘길 때 `hanlint 글.md --severity all` 의 notice 를 읽고 판단한 것을 함께 적는다.

## 지킬 것

- primer 와 본보기와 문형의 예시는 규칙을 보이는 자료다. 그 문장과 숫자를 결과의 사실로 옮기지 않는다.
- 규칙이 정당한 문장을 잡았으면 끄고 넘어가지 않는다. 그 문장과 이유를 사용자에게 보이고, 끌지는 사용자가
  `hanlint.toml` 의 `disable` 이나 `<!-- hanlint-disable <규칙> -->` 로 정한다.
- 규칙 여럿이 한꺼번에 안 맞으면 `--preset`을 먼저 다시 보되 정당한 문장의 오탐 가능성도 확인한다.
- error 0 을 좋은 글의 합격 판정으로 부르지 않는다.

## 더 있는 것

사실 계약 (brief, guard), 근거 원장 (evidence), 블라인드 사람 평가 (arena), 승인 고침 기억 (learn) 은
`skills/specs/operation/writingAxis.md` 가 소유한다. 사람 평가 30건이 모이기 전에는 기본 절차에 넣지 않는다.
