# 리듬 악보 탐침 1회차 (2026-09-02)

커밋 `eeb2e7d` 위에서 잰다. 말뭉치 지문 표는 2026-08-29 판 (1,600편). 악보는 `probeRhythmScore.py score --seed 42`
로 뽑았고 문단 다섯, 문단당 문장 2~6개, 평서문의 문체가 요청과 같은 문단만 골랐다.

## 물음

편집된 실제 문단의 모양 (문장 수, 어절 수, 끝맺음) 만 주면 모델이 그 모양을 채우는가. 채우면 초안의 문장 길이
분포가 사람 글의 띠로 옮겨 가는가. 결함 (error, notice) 은 어떻게 되는가.

## 설계

요구 셋 (primerRound1 과 같은 것. blog 합니다체 Polars 엑셀 합치기, docs 한다체 `tablecheck.toml` 형식, report
한다체 8월 장애 보고). 조건 둘. plain 은 요구만, score 는 요구에 앞서 악보 파일을 읽으라는 지시. 글쓴이는 이 세션과
같은 모델의 fresh-context 서브에이전트 (general-purpose) 여섯. 저장된 첫 초안을 `measure` 로 재고 사람이 고치지
않았다.

악보 (seed 42, 어절 수와 끝맺음):

```text
blog   문단 1: 22(니다) 35(니다) / 2: 10 8 19 13 14 14 (전부 니다) / 3: 16 16 18 15 6(것이다) 17 / 4: 17 10 / 5: 13 13 19
docs   문단 1: 11(다) 17(다) / 2: 14 7 / 3: 13(다) 12(것이다) / 4: 8 23 / 5: 29 8
report 문단 1: 22(것이다) 15 15 15 9 / 2: 26 14 20 / 3: 10 16 3 6 7 / 4: 5 16 28 / 5: 7 16 18 (전부 다)
```

## 사람 띠 (같은 지문 표, 문서 단위, 문장 8개 이상인 문서)

초안이 사람 글의 분포 안에 드는지 볼 기준이다. 편집된 글은 세 종류 모두 문장 길이 변동 계수가 0.4 근처다.

| 종류 | 문서 | 문장 길이 변동 계수 25/50/75 | 문장 길이 중앙값 |
|---|---:|---|---:|
| blog 합니다 | 7 | 0.39 / 0.43 / 0.44 | 12 |
| technicalDocs 한다 | 193 | 0.38 / 0.41 / 0.46 | 11 |
| report 한다 | 198 | 0.36 / 0.43 / 0.51 | 15 |

## 관찰 (판정 아님)

1. **모양은 그대로 옮겨진다.** 세 편 모두 악보의 문단 모양을 ±3어절 안에서 따랐고 것이다 자리까지 같았다. docs 는
   악보 다섯 문단을 전부 (11/17 → 13/16, 14/7 → 15/7, 13/12 → 15/11, 8/23 → 7/22, 29/8 → 30/8), report 는 앞 세 문단을,
   blog 는 앞 두 문단을 채우고 요구 길이에서 멈췄다. 모델이 못 세는 것은 "길이를 섞어라" 같은 지시이고, 채울 모양을
   주면 센다.
2. **꼬리도 옮겨진다.** blog 악보 첫 문단의 35어절 문장이 37어절로 나와 longSentence error 와 outsideProfile 둘을
   냈고, docs 악보의 29어절이 30어절로 나와 outsideProfile 을 냈다. 실제 문단을 그대로 뽑으면 그 문단의 꼬리
   (그 종류 상위 1%) 가 함께 온다. 악보로 쓸 문단은 문장 길이가 그 종류의 p10~p90 안인 것만 고르는 것이 맞다.
3. **plain 초안의 문장은 사람보다 짧다.** 중앙값 7~10어절 (사람 11~15). 악보는 이것을 사람 중앙값 (14~16.5) 으로
   옮겼다. 변동 계수는 blog 에서 사람 띠 밖 (0.35) 에서 안 (0.42) 으로 들어왔고, docs 와 report 는 이미 띠 안이었고
   그대로다.
4. **결함 수는 늘지도 줄지도 않았다.** error 4 → 3, 0 → 1, 0 → 0. notice 3 → 4, 0 → 2, 3 → 1. 악보가 바꾼 것은
   리듬이고 결함은 다른 축이다. 악보의 긴 문장 꼬리가 만든 error 하나 (longSentence) 는 2번을 고치면 사라진다.
5. **blog 말뭉치가 약하다.** 합니다체 blog 는 7편이고 전부 Kubernetes 한국어 블로그 (번역) 라 끝맺음이 니다로
   단조롭고 문장이 길다. 악보가 그 성질을 그대로 전달한다. 이 종류의 악보는 다른 자료원이 들어오기 전에는 믿지
   않는다.
6. **회차 사이 흔들림.** 같은 plain 프롬프트가 primerRound1 (오전) 에서는 1,313~1,718자, 이번엔 644~832자를 냈다.
   한 회차의 짝 셋으로는 어느 방향도 결론이 아니다.

## 다음 회차에 바꿀 것

- 악보 문단을 그 종류의 문장 길이 p10~p90 안에서만 고른다 (2번).
- 요구 셋 × 조건 둘 × 2회로 열두 편. 문장 길이 중앙값과 변동 계수, error, notice 를 같은 표로.
- 악보의 끝맺음이 endingRepeat 이 notice 로 잡는 연속을 그대로 들고 오는 문제 (사람 글이 그렇다) 는 규칙 쪽 질문이다.
  여기서 손대지 않고 적어 둔다.

## 초안 지문

# 리듬 악보 탐침 2회차 (2026-09-02, 커밋 691e625 뒤)

1회차의 "다음 회차에 바꿀 것" 을 그대로 했다. 악보 문단을 그 종류 문장 길이의 p10~p90 안에서만 골랐고 (blog 7~23어절,
docs 6~19, report 7~28), 요구 셋 × 조건 둘 × 2회로 열두 편을 썼다. 반복마다 악보를 다르게 줬다 (seed 42, 43).
글쓴이와 측정은 1회차와 같다.

(endingRepeat 5, factListParagraph 0), 글자 691~972.

## 관찰 (판정 아님)

1. **문장 길이는 여섯 편 모두 사람 중앙값 (11~15) 으로 옮겨 갔다.** plain 여섯 편은 6~7.5어절로 회차를 넘어 한결같이
   사람보다 짧다. 악보 여섯 편은 10~16 이다. 1회차와 같은 방향이고 열두 편에서도 예외가 없다.
2. **꼬리를 자르니 다양성도 잘렸다.** 악보 편의 변동 계수 평균 0.307 은 사람 띠 (0.36~0.51) 아래고 docs 악보 1 은 0.18
   이다. p10~p90 문단만 뽑으면 그 문단들이 사람 문단 가운데 고른 것들이다. 다음은 p5~p95 로 넓히거나, 문단의
   문장 길이 퍼짐 (표준편차) 이 그 종류의 중앙값 근처인 문단을 고르는 쪽이 맞다.
3. **notice 는 18 → 7 로 줄었고 factListParagraph 는 7 → 0 이다.** 악보가 문단을 2~5문장으로 고정하고 문장이 길어져
   사실 나열 문단의 꼴 (짧은 문장 셋 이상, 인과 표지 없음) 이 사라진 것으로 보인다. endingRepeat 은 8 → 5 다.
   error 는 5 → 5 로 같다. blog 의 error 는 두 조건에서 같은 것 (cliche `이 글에서는`, noQuestion, installImport 의
   fastexcel) 이라 리듬이 아니라 내용과 종류의 문제다.
4. **길이는 조금 늘었다.** 악보 편 평균 812자 (plain 716자), blog 악보 2 는 972자로 요구 상한 900 을 넘었다. 악보가
   문단 다섯을 채우게 하니 요구 길이와 겨루는 것이다. 문단 수를 요구 길이에서 역산해 주는 것이 맞다.
5. **모양 따르기는 1회차와 같다.** 열두 편 모두 지정 문단 수 (5) 를 그대로 냈고 plain 은 6~7 문단을 썼다.

## 다음에 잴 것

- 문단 고르기를 p5~p95 또는 퍼짐 중앙값 근처로 바꾸고 변동 계수가 사람 띠로 돌아오는지.
- 문단 수를 요구 길이에서 역산 (종류의 문단당 글자 수 중앙값으로 나눔) 해 길이 초과가 사라지는지.
- 위 둘이 되면 `hanlint score` 로 제품에 넣을지 정한다. 넣는다면 primer 의 짝이고 hook 의 쓰기 전 단계다.
