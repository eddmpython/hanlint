# 구조화 사실 계약 탐침

날짜: 2026-08-31

## 물은 것

일반 요구와 비교 프로파일을 한 프롬프트에 섞지 않고, 버전 고정 brief만 생성 모델에 주면 다음 두 가지를
분리할 수 있는가.

1. 모델이 더 잘 쓰는가.
2. 제품이 요구 밖 사실 표면과 형식 위반을 빠짐없이 막는가.

앞선 `writingLift` 탐침에서 일반 brief보다 안전하게 나은 생성 조건은 없었다. 특히 여러 글의 공통 문형을
함께 준 v1 패킷은 다른 과제의 수치와 문장을 끌어와 사실 표면 통과가 0/7이었다. 이번 탐침은 생성 향상을
주장하지 않고 두 번째 질문만 제품 코드로 검증한다.

## 설계

- 일곱 프리셋마다 독자, 과업, 한 문장짜리 원자 사실, 필수 표면, 허용 숫자, 금지 표면과 글자 수 범위를
  `writingBrief` v1에 넣었다.
- 구조화 `writingPacket`에는 프로파일, 규칙 문형, 다른 글과 승인 패치를 넣지 않았다. `input.brief`만 사실
  재료로 두었다.
- `qwen3:8b`에 각 패킷을 한 번씩 주었다. 옵션은 `temperature=0`, `seed=42`, `num_predict=1200`,
  `think=false`다.
- 생성 결과는 수정하지 않고 제품의 `guardText`로 채점했다. 필수 표면, 숫자, URL, 코드, 링크 목적지,
  금지 표면, 길이와 hanlint error를 각각 셌다.
- `contractSatisfied`는 이 결정적 검사만 모두 통과한 경우다. 사실 관계와 진실, 빠진 의미, 금지 주장의
  바꿔 말하기, 유용성과 자연스러움은 포함하지 않는다.

원자 사실로 나누는 선택은 긴 글의 사실성을 한 덩어리 합격으로 보지 않고 각 원자 사실의 근거 여부로
평가한 [FActScore](https://aclanthology.org/2023.emnlp-main.741/)와 같은 방향이다. 다만 이번 guard는
근거 문서가 그 의미를 뒷받침하는지 판정하지 않고 글자 표면만 확인한다.

## 탐침이 제품에서 먼저 찾은 결함

첫 예비 판은 `facts`의 숫자만 허용해 `task`의 `2주`를 요구 밖 숫자로 잘못 잡았다. 숫자 계약의 범위를
`reader`, `task`, `facts` 전체로 고치고 v2 입력과 출력을 만들었다.

v2 출력의 첫 채점에서는 원문 URL을 같은 목적지의 마크다운 링크로 감싼 결과를 새 URL과 새 링크로
오인했다. URL이 닫는 대괄호 앞에서 끝나게 하고, brief에 원문으로 든 목적지를 링크로 감싸는 변환은
허용했다. 또 `1,2`를 12로 합치지 않고 세 자리 천 단위 묶음만 정규화하도록 숫자 경계를 좁혔다. 이 수정과
한계 문구 변경으로 패킷 해시가 달라졌으므로 최종 v3 패킷에서 일곱 결과를 다시 생성했다. 아래 수치는
그 원출력을 제품 코드로 채점한 v4 결과다.

구조화 패킷이 자연스러운 글을 만들었다는 근거는 없고, 요구 길이도 1/7만 맞았다. guard는 자동 계약을
어긴 결과 6개를 종료 코드 1로 막았다. 자동 계약을 통과한 한 결과도 의미상 사실과 품질의 합격으로 부르지
않는다. 제품의 이번 가치는 생성 점수 상승이 아니라 명시한 실패를 거짓 통과시키지 않는 데 있다.

## 연구와 제품 경계

[RAG](https://papers.neurips.cc/paper/2020/hash/6b493230205f780e1bc26945df7481e5-Abstract.html)는
명시적인 외부 기억을 검색해 지식 집약 과제의 구체성과 사실성을 높일 수 있음을 보였다. 그러나 이 저장소의
완성 글 실측에서는 여러 글의 문형과 수치를 생성 프롬프트에 넣자 사실 오염이 커졌다. 따라서 잘 쓴 글 DB는
당장 문장을 공급하는 재료가 아니라 종류, 독자 상태, 수사 기능, 지문 분포와 승인 전후의 대조 원장으로
쓴다. 원문 구절을 생성에 넣는 검색은 별도 짝 비교에서 안전 승을 보일 때만 연다.

[ALCE](https://aclanthology.org/2023.emnlp-main.398/)는 검색, 생성, 인용의 정확성과 완전성을 따로 평가한다.
다음 사실층도 URL이 있다는 이유로 참이라고 부르지 않고, 원자 사실마다 고정된 근거 조각과 출처 판을
연결한 뒤 인용 완전성과 함의를 별도 평가해야 한다.

[G-Eval](https://aclanthology.org/2023.emnlp-main.153/)은 기준별 LLM 평가가 사람 판단과 더 가까워질 수 있음을
보였지만, LLM이 만든 글을 선호하는 편향도 보고했다. 자연스러움 평가를 하나의 모델 점수로 제품 합격에
넣지 않는다. 일반 brief 기준과 후보를 이름을 가린 짝으로 섞고, 자리 순서를 바꾸며, 사람 평가와 평가 모델
둘을 기록해야 한다.

## 다음 실험

다음 층은 자동 재작성기가 아니라 근거 원장과 블라인드 대조 장치다.

1. 각 원자 사실에 선택적인 `evidence` 조각, 출처 URL, 고정 판, 라이선스와 확인 시각을 붙인다.
2. 초안의 문장을 원자 주장으로 분해하되, 기계가 확정하지 못한 분해와 함의는 검토 대기 상태로 둔다.
3. 잘 쓴 글 DB에서는 문장 전문보다 종류, 수사 기능, 독자 상태, 문단 지문과 사람이 승인한 국소 전후 짝을
   검색한다.
4. 새 검색 전략은 항상 일반 brief와 같은 입력으로 짝 생성한다. 사실 계약을 둘 다 통과한 결과끼리만
   블라인드 자연스러움과 독자 과업 완수율을 비교한다.
5. 안전 승이 없는 검색 결과는 생성 패킷에 넣지 않고 평가 화면에만 남긴다.

이 순서라야 hanlint가 “그럴듯한 문장을 많이 보여 주는 도구”가 아니라 요구, 근거, 초안, 검증과 사람
승인을 추적하는 작문 컴파일러가 된다.
